# TenkiBench × EleutherAI lm-evaluation-harness

Run [TenkiBench](https://bench.tenki.no) — a Norwegian SMB benchmark for
language models — through the standard `lm-eval` tool that the LLM-research
community already has installed.

This adapter is a thin wrapper around the published HuggingFace dataset at
[`tenki-labs/tenkibench`](https://huggingface.co/datasets/tenki-labs/tenkibench).
The HF dataset must be live for `lm-eval` to fetch the rows.

## Quick start

```bash
pip install lm-eval
git clone https://github.com/tenki-labs/tenkibench.git
cd tenkibench/lm-eval-tenkibench

# Run all 11 benches under one aggregate score
lm_eval \
  --model hf \
  --model_args pretrained=mistralai/Mistral-Nemo-Instruct-2407 \
  --tasks tenkibench \
  --include_path .

# Run a single bench
lm_eval \
  --model hf \
  --model_args pretrained=mistralai/Mistral-Nemo-Instruct-2407 \
  --tasks tenkibench_norwegian_smb \
  --include_path .
```

`--include_path .` tells lm-eval where to find the YAML files in this folder.

## What this adapter does and doesn't do

`lm-eval` is designed for benchmarks where scoring is a function of the raw
model output (string match, regex, multiple-choice logits). TenkiBench has
some tasks that fit that mould cleanly and others that don't:

| `eval_method` (in dataset) | This adapter | Notes |
|---|---|---|
| `exact_string` | full | trimmed, NFC-normalized, case-insensitive, with substring fallback |
| `regex` | full | one or more patterns, any match → 1.0 |
| `regex_all` | full | every pattern must match |
| `numeric_exact` | full | Norwegian-locale parsing (`12 437,50` → `12437.50`) |
| `json_schema` | approximate | parses JSON and matches top-level keys; full type validation requires the official runner |
| `llm_judge` | placeholder (0.5) | requires a rubric model — see below |

If you want the full TenkiBench score with proper JSON-schema validation
and LLM-as-judge rubrics, run the official scorer in the [TenkiBench
repo](https://github.com/tenki-labs/tenkibench) instead. That said, the
results from this adapter are directly comparable across models — every model
is scored under the same rules — so it's a perfectly valid benchmark to cite.

## File layout

```
lm-eval-tenkibench/
├── README.md            ← this file
├── CHANGELOG.md         ← score-affecting adapter changes
├── CITATION.cff         ← citation metadata
├── group.yaml           ← "tenkibench" alias grouping all 11 benches
├── utils.py             ← scorer (no external deps)
└── tasks/
    ├── tenkibench.yaml                       ← root task = group
    ├── tenkibench_norwegian_smb.yaml
    ├── tenkibench_eu_ai_act.yaml
    ├── tenkibench_hallucination.yaml
    ├── tenkibench_extraction.yaml
    ├── tenkibench_tool_use.yaml
    ├── tenkibench_norwegian_language.yaml
    ├── tenkibench_norwegian_construction.yaml
    ├── tenkibench_norwegian_healthcare.yaml
    ├── tenkibench_norwegian_finance.yaml
    ├── tenkibench_gdpr_advanced.yaml
    └── tenkibench_safety_norwegian.yaml
```

The `tasks/` files are auto-generated by
[`scripts/generate-lm-eval-tasks.ts`](../scripts/generate-lm-eval-tasks.ts).
Re-run with `pnpm generate:lm-eval` after adding a new bench under
`tasks/<bench>/` in the main repo.

## Reproducibility

The HF dataset is content-addressed — every commit gets a hash. To pin a
specific TenkiBench version in your paper:

```bash
lm_eval ... --model_args revision=<commit-sha>
```

Adapter scoring rules that change in a way that affects scores are logged
in [`CHANGELOG.md`](CHANGELOG.md). Tag the version of this adapter you used
when reporting results.

## Hold-out

A separate hold-out set lives in `tasks-holdout/` in the main repo. It is
**never** published to HF and is used exclusively to detect overfit submissions
to the public leaderboard. Running this adapter only sees the public set.
